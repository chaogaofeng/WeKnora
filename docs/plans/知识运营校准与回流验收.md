# 知识运营校准与知识回流验收

> 2026-10-26。配合 v1.3 工作台使用。自动测试验证工程契约，本清单验证真实业务效果；未执行项不能记为通过。没有自动启用、历史回填、自动发布或原文/Wiki 修改。

## 1. 样本与口径

按 RAG（含快速与 Agent）、Wiki、混合三种模式采集启用后的新问答。每条样本保存运行 ID、诊断版本、模型 ID/配置、策略版本、原问题/实际改写、当时材料、人工结论与依据。复核者依据原始业务材料独立判断，随后对照机器诊断，不以模型自报置信度作为真值。

先跑下表的功能样本，再用真实问题扩展。下表不能代替业务代表性抽样；样本量、各层误差及可接受阈值由业务方明确后写入校准说明，不能从少量演示样本外推总体准确率。

| 用例 | 模式 | 安排 | 验收重点 |
| --- | --- | --- | --- |
| C01 | 快速 RAG | 原文完整支持单轮问题 | 支持判定有当时正文引用，正文完整不等于业务事实已全面验证 |
| C02 | Agent RAG | 多次搜索与文档读取 | 候选材料与实际模型输入分开，使用到的正文可追溯 |
| C03 | Wiki | 页面与关联原文一致 | 回答支持和来源比较分别展示，事后原文不充当当时依据 |
| C04 | 混合 | 同时使用 Wiki 与原文 | 实际工具路径、两类正文可见；同源材料不算两份独立佐证 |
| C05 | 混合 | 合理地只用一种来源回答 | 不因未使用另一类工具而自动判错 |
| C06 | 三模式分别跑 | 单轮改写改变对象或否定词 | 对照原问题与改写，不因材料支持改写后的问题就认为原需求满足 |
| C07 | 三模式分别跑 | 多轮“展开第三项”，有明确历史 | 轮次、会话 ID、实际历史和改写可检查，不把历史模型回答当权威资料 |
| C08 | 三模式分别跑 | 多轮代词指代缺失 | 明确缺口，不编造前文，也不当作闲聊免核验 |
| C09 | 三模式分别跑 | 纯感谢/告别且回答无业务论断 | 不形成无意义的知识补证/回答复核待办 |
| C10 | RAG | 正文缺少关键条件，回答却给确定结论 | 展示具体论断及缺失条件，区分证据不足与反证 |
| C11 | Wiki/混合 | 页面明确省略原文例外 | 识别具体差异；适用时间/对象不同不能直接视为冲突 |
| C12 | Wiki | 正文完整但历史关联版本不明 | 支持性与版本限制分开；可接受已调查限制并关闭跟进，原缺口仍在 |
| C13 | 任意模式 | 用户取消或工具异常 | 技术事项可调查并关闭，原运行状态保持 cancelled/failed |
| C14 | 任意模式 | 人工判可用，机器仍不可核验 | 两结论独立保存；通过只是允许整理草稿，不自动写知识 |
| C15 | 任意模式 | 新诊断或另一人先处置 | 旧页面提交失败需刷新，旧关闭结果不沿用到新版本 |

## 2. 校准记录应包含什么

- 各模式/渠道/风险层样本数和时间范围，正常与异常样本都包含；保留样本运行 ID。
- 机器判为支持、人工判需修订的数量，以及机器报异常、人工判可用的数量。后者需区分“业务上可用但当时证据不足”，不能全部称为模型误报。
- 已判错样本的具体问题、实际原因、机器原因是否有依据；此项由离线质量评估完成，不增加日常根因复核表单。
- 自动记录候选的抽检结果及风险接受范围；模型/策略/诊断预算改变后重新验证并确认。
- 延迟与资源：排队时长、诊断中位/长尾耗时、失败类型、单条 token 和日调用量。没有价格配置时不把 token 数换算为费用。

自动记录的校准确认是管理员对上述依据的登记，不是系统已自动证明准确率。未登记、绑定失效或模型配置不可核对时，保守进入人工复核。

配置并发验收：打开设置页后，在模型管理中修改同一模型配置，再用旧页面确认，必须提示配置已变化并保留输入。切换诊断模型时，必须等新配置核对完成才可确认；返回较晚的旧请求不能覆盖新模型或另一租户的草稿。实际执行的模型配置与确认不一致时，即使数据库后来恢复原配置，该次结果也不能自动记录。Ollama 服务地址改变后需重新确认。使用租户/环境继承云凭据而无法完整绑定配置时，保持诊断与人工复核，不开启自动记录。

## 3. FAQ 真实回流验收

使用专门的测试 FAQ 库及可辨识的测试问答。确认该库可写、Embedding/索引可用，并加入 RAG/混合检索范围。测试数据由验收人明确发布及管理，不能把后台模拟发布当作真实结果。

1. 对一条当前诊断保存“通过 · 回答可用”。记录复核 ID；机器报告和原聊天内容不变。
2. 打开“采纳为知识”，把问题整理为不依赖前文的完整问题；检查渲染答案、内部引用清理与代码示例保留。
3. 明确发布，记录采纳 ID、目标 FAQ 库、FAQ ID、索引成功状态。断连先刷新；失败按原快照重试，不反复创建。
4. 新会话分别用快速 RAG、Agent RAG、混合模式提出原问题及合理改述。检查真实工具调用与召回材料中是否出现该 FAQ，并记录新运行 ID。
5. 对照入库前后回答的完整性、正确性与适用范围，记录人工判断。若只看到索引成功，结论只能是“已发布”，不能写“已改善”。
6. 纯 Wiki 按默认工具范围不预期召回 FAQ；若要覆盖纯 Wiki，需另行设计 Wiki 知识处置，不偷偷改变当前模式。
7. 更改人工复核不会自动撤回已发布 FAQ；测试结束按 FAQ 管理流程处理测试知识。

| 阶段 | 可确认的事实 | 不能据此推断 |
| --- | --- | --- |
| 人工通过 | 回答被复核者判为可用 | 已发布、机器证据完整 |
| FAQ 已索引 | 知识具备参与召回的条件 | 一定命中、三模式均能使用 |
| 实际召回命中 | 本轮使用了该 FAQ | 答案一定改善 |
| 人工对照验证 | 这些样本的回答得到改善 | 全量问题准确率提升 |

## 4. 本轮工程验证与容量边界

后端真实 FAQ 服务的隔离集成测试覆盖创建/恢复、索引状态门禁、冲突内容不覆盖、发布后可检索状态；索引适配器由受控测试替代，不伪称已调用真实 Embedding 或外部向量服务。

本地评估基线为 9 条运行（6 RAG、3 Wiki）、13 版分析、3 条人工复核、0 条采纳；12 次成功诊断平均约 55 秒。这是开发样本，不是容量指标，也没有混合模式和真实 FAQ 回流验收结论。

当前每实例串行诊断，列表按权限遍历运行。扩量前用独立测试库按预期保留量和访问量测量列表延迟、数据库查询量、队列等待及每租户资源消耗；再决定批量读模型、并发和保留期，不先提高并发制造额外模型费用。
