## 0. 目标、范围与事实边界

### 0.1 业务目标

面向供应链金融中的合同审核流水线与智能客服，解决两组问题：

1. **回答质量**：回答有没有得到实际证据支持，是否遗漏关键条件，是否存在错误推断；未来在证据不足、冲突或超范围时可靠拒答。
2. **知识质量**：发现原文和 Wiki 的错误、冲突、过期与缺口，形成可审核的处置任务，并验证处置是否改善实际问答。

整体保留四层结构：L1 观测 → L2 诊断 → L3 经审批的知识处置 → L4 在线防线。**当前一期覆盖 L1、L2 及诊断结论复核，完整顺序为：观测 → 回答验证 → 根因诊断 → 风险分流 → 人工复核或抽检 → 结论留存。** 低风险且满足条件的结果自动记录；人工集中处理重要、存疑和抽中的案例，不要求逐条审核全部问答。

L3 知识处置与 L4 在线防线属于后续范围。当前可以写入运营证据、诊断和复核记录，但不修改知识，不自动修复、不发布、不归档，也不因人工确认诊断而触发知识变更。

“被现有证据支持”不等于“业务事实一定正确”，“回答有问题”也不直接等于“知识有问题”。

### 0.2 三类业务模式与两种执行方式

| 业务类型 | 典型配置 | 主要证据来源 | 需要特别关注 |
|---|---|---|---|
| RAG 问答 | `quick-answer`，或 `smart-reasoning + rag-qa` | 原文分块、FAQ、文档读取结果 | 快速流水线与 Agent 检索不能混为同一执行方式 |
| Wiki 问答 | `smart-reasoning + wiki-qa` | Wiki 搜索摘要/片段、页面正文，必要时回查原文 | 页面由资料加工生成，回答支持性与页面来源一致性分开验证 |
| Wiki + RAG | `smart-reasoning + hybrid-rag-wiki` | Wiki、原文检索和文档读取的实际组合 | 配置允许两类工具，不代表本次真的查过两类证据 |

模式是默认工作配置，不是不可变的执行保证。预设工具、提示词可被修改；新问答按运行时配置记录快照，不能用事后配置覆盖当次事实。

采集和报告同时保留：`channel`、`qa_type`、`execution_mode`、`agent_id`、配置版本/快照、实际来源类型和工具调用。不开发旧问答的模式推断与数据转换；新问答采集不到的字段明确保留 unknown。

Wiki 默认通过文本/正则搜索与页面链接导航，不依赖向量检索；`read_document` 按标识读取原文或在文档内匹配文本。增加 `search_knowledge` 或使用混合模式后，才可能调用相应的语义/混合检索。Wiki-only 知识库不保证存在向量索引。

### 0.3 当前代码可复用的能力与限制

| 能力 | 可复用部分 | 不成立的原假设 |
|---|---|---|
| `messages.knowledge_references` | 部分 RAG 的分块正文、来源与检索信息 | 不是所有 Agent/Wiki 问答的完整证据集合；分数不保证齐全 |
| `agent_steps` | 已持久化的工具调用和结果 | `read_document` 等结果会在持久化前裁剪；记录了调用不等于保存了全部正文 |
| Wiki 搜索/读取 | 可以保留工具输出中的摘要、正文和来源线索 | 页面读取有预算截断；返回结果没有明确绑定页面版本 |
| `modelcontext` | 来源身份、可引用范围与引用展开 | 合法引用不代表语义支持；无引用标签也不代表无依据 |
| Wiki 页面与修订 | 当前页面、历史正文、问题登记、编辑与修复工具 | 历史可能被清理，修订不包含完整历史来源关联，不能无条件还原当时证据链 |
| 既有编辑服务与任务队列 | 复用写入权限、修订、索引任务、重试和死信能力 | 审批成功不等于执行成功，更不等于索引/Wiki 更新完成或回归通过 |
| 现有评测服务 | 数据集处理、部分评测基础设施 | 当前固定 RAG 评测不能等同于 Wiki/混合 Agent 的原模式回归 |
| Langfuse | 启用且成功留存时可提供调用追踪、辅助评估 | 不是业务证据存储前提，trace 标识存在不代表正文已留存，不能恢复从未采集的历史 |

关键代码依据：
- `internal/types/custom_agent.go`、`config/agent_type_presets.yaml`：模式与类型预设。
- `internal/application/service/session_knowledge_qa.go`、`session_agent_qa.go`：两类执行链路。
- `internal/agent/tools/wiki_tools.go`、`read_document.go`、`persist.go`：证据读取、预算与持久化裁剪。
- `internal/types/agent.go`：Agent 检索引用集合目前存在收集缺口。
- `internal/types/wiki_page.go`：来源关联、页面版本和修订范围。
- `internal/application/service/evaluation.go`：固定 RAG 评测调用。

本地环境是测试环境；本地样本数量、模式比例和 Langfuse 数据量均不能代表真实业务环境。一期只验证当前入口及新增采集覆盖，不盘点旧问答留存区间，不设置历史回填起止时间。

## 1. 验证对象与判定纪律

### 1.1 两层验证，分别给结论

| 层次 | 问题 | 阶段 |
|---|---|---|
| 回答证据支持性 | 该论断是否得到当时实际提供给模型的证据支持？是否忽略限制条件或与证据矛盾？ | 一期 |
| 知识内容及适用性 | Wiki 是否忠实于来源？来源是否有效、过期、互相冲突或不适用于当前对象？ | 一期对异常、高风险及抽检案例按需只读诊断；全库主动扫描后续扩展 |

例如：原文写“成立满一年”，Wiki 写“成立满两年”，回答也写“两年”。回答可以获得“Wiki 证据支持”的结论，但 Wiki 与原文可能不一致。不能把前者显示为已完成业务事实核验。

Wiki 证据未做来源核验时，展示：“回答得到 Wiki 内容支持；原始资料一致性未核验。”不默认把所有 Wiki 内容视为不可靠，也不强制所有概览问题都回查原文。

### 1.2 当时证据与事后补查严格分开

- **回答时证据**：实际进入模型上下文的可读内容，记录获取顺序、来源、范围、截断状态及版本信息。工具返回的候选全集不自动等于模型看见的全集。
- **事后核验材料**：验证器或专家后来检索的资料，用来判断知识问题或调查缺口。独立标记获取时间和版本，不能反向证明回答时已有依据。
- **证据缺失**：只剩 ID、调用参数、摘要占位符或可变来源地址时，不能假装拥有当时正文。哈希用于校验，不能替代正文。
- **历史和外部上下文**：多轮对话、用户附件、引用文本、长期记忆、MCP/网页内容可能影响回答。纳入实际使用的来源；未支持的来源标记覆盖缺口，不能静默忽略后给出全量结论。
- **Wiki 与原文同源**：两者一致不等于两份独立证据；保留派生关系，不以来源数量叠加置信度。

### 1.3 质量判定与可验证性分开存储

至少分开以下维度，不使用单个 `no_evidence` 包办：

| 维度 | 建议取值/含义 |
|---|---|
| 正文采集完整性 | complete / partial / missing / unknown，表示回答时模型可见的知识正文是否完整保存；来源版本缺失不单独降低此项 |
| 来源可追溯性 | known / pending / unknown，分别表示来源版本已记录、存在来源追溯缺口、无法确认；与知识来源一致性核验分开 |
| 证据获取结果 | obtained / no_match / not_attempted / tool_failed / unknown |
| 验证任务状态 | pending / running / succeeded / failed / skipped |
| 论断判定 | supported / partial / contradicted / unsupported / unverifiable / not_applicable |
| 诊断任务状态 | pending / running / succeeded / failed / skipped；succeeded 仅表示处理完成，根因仍可能 unresolved |
| 根因结论 | suspected / evidence_backed / unresolved，另存根因类别、事实依据与待确认点；有证据支持仍不等于人工确认 |
| 分流结果 | auto_record / human_review / quality_sample / technical_followup / needs_evidence，记录理由、风险规则与策略版本 |
| 人工复核状态 | unreviewed / confirmed / corrected / needs_more_evidence；回答判定与根因结论分别复核 |
| 知识来源核验 | not_checked / consistent / inconsistent / unresolved |

`unsupported` 表示在足够完整的已采集上下文中未找到支持，`contradicted` 表示存在直接反驳；两者均不自动等于知识错误。正文或上下文采集缺失时，部分证据仍可支撑个别论断，但不能给整条回答无条件“完全支持”。仅缺来源版本或 Wiki 关联摘要版本时，已保存正文仍可支持全部论断；保留 `supported` 并明确限定为“已采集的回答时正文支持”，将来源版本缺口单独展示并阻止自动记录，不把版本缺失等同于回答内容缺乏支持。来源补查不完整另记为 `unresolved`。模型原始判定与系统调整后的判定及调整理由分别保存在诊断报告中，旧版未保存的信息不反推、不回填。

`not_applicable` 用于没有待核验知识论断的内容，如纯澄清问题；可靠拒答另按适用业务规则评估，不能直接当作错误。数字、期限、清单和结论中的条件、例外、否定词重点检查；缺少标点式引用不是无依据判定条件。

工作台通过只读派生字段 `run.coverage` 展示正文与来源版本两个维度；原始 `capture_status`、`gaps` 及已有诊断保留。仅来源版本缺失的已完成问答可显示“正文完整 / 来源版本待核验”；正文丢失、未知缺口、未完成采集或缺失原因不明时，不推定正文完整。列表、详情、待复核和总览统一口径，分别通过 `content_status` / `provenance_status` 筛选。总览新增 `content_coverage`、`content_coverage_by_mode` 和 `provenance_counts`；旧聚合字段保持原义。此展示拆分不放宽自动记录、来源一致性核验及复核规则，不迁移或补写历史数据。

结构化 API 输出按字段路径和论断定位，支持 JSON 结论、意见、依据字段，不假设答案一定是带引用标签的自然语言段落。记录论断的答案位置、证据定位、判定原因与不确定性。

## 2. 一期：观测、验证、根因诊断与重点复核

### 2.1 一期目标与边界

目标：对三类问答形成**证据覆盖、回答支持性和根因诊断报告**，在进入人工队列前完成可自动完成的证据整理、来源比较与原因排查。专家看到“事实、疑似原因、支持与反对证据、仍需裁决的问题”，减少逐条重查，同时区分无法验证、回答错误与知识问题。

- 验证异步执行，不在回答路径内调用验证模型，不拦截线上回答。
- 只采集功能启用后新发起的问答，不读取旧消息批量重建运营记录，不开发历史适配器、旧问答扫描器或回填入口。为新问答增加最小采集接入，不承诺“问答链路零改动”或“零采集成本”。
- 默认关闭功能；关闭时不采集新问答正文、不创建或执行新的诊断任务，问答行为保持兼容。已有任务按模块停机策略收尾或暂停，再启用时仅恢复已纳入运营的任务；不补采关闭期间的问答。
- 采集故障不能令问答失败，但必须记录覆盖缺口和告警，不声称零额外耗时或绝不丢失。
- 一期仅允许写入本模块的运行、证据、验证、诊断、分流和复核记录。禁止修改原文、chunk、Wiki、FAQ，禁止重解析、归档、重新生成及自动修复；人工复核确认也不触发这些动作。
- 可读取并关联现有 Wiki issues，但当前不调用 `wiki_flag_issue` 等修改 Wiki 台账的工具；运营问题保存在本模块，后续处置阶段再衔接既有治理能力。
- “较完整诊断”指形成可追溯的证据链和可裁决的问题，不承诺每个案例都能自动确定真实根因。证据、权限或历史版本不足时明确保留未知。

### 2.2 统一证据记录

在业务核心字段之外建立独立证据记录；优先集中保存最小必要的实际可读内容，不改变现有 `messages` / `agent_steps` 的对外格式和历史裁剪规则。

建议概念模型如下，落地时再映射成具体迁移和接口：

| 记录 | 必要信息 |
|---|---|
| 问答运行记录 `knowledge_ops_runs` | tenant/session/message/request、channel、qa_type、execution_mode、agent/model、当次非敏感配置快照及 hash、完成/取消/失败原因、schema_version、采集完整性与缺失原因 |
| 证据记录 `knowledge_ops_evidence` | run、来源类型、来源租户/KB/文档/chunk/页面 ID、页面 slug、版本或 unknown、工具调用/轮次、正文或不可变正文存储引用、内容 hash、读取范围、截断/省略、获取时间、是否实际送入模型 |
| 验证记录 `knowledge_ops_verifications` | run、答案及证据版本、claims、判定维度、验证模型实际版本、prompt/policy 版本、任务状态；保存机器原判定 |
| 诊断记录 `knowledge_ops_diagnoses` | 关联验证版本、诊断范围、观察事实、根因候选、支持/反对证据、来源比较、未知项、补查轨迹、模型/策略版本、问题组与诊断状态 |
| 分流记录 `knowledge_ops_triage` | 关联诊断版本、风险规则、分流理由、目标队列、抽样层/入选概率、预算降级原因；策略变化或重分流保留历史 |
| 复核记录 `knowledge_ops_reviews` | 关联验证/诊断版本、复核对象（回答或根因）、人工结论、人员/时间/理由/依据、前一记录引用；追加保存，不覆盖旧结论 |
| 任务记录 `knowledge_ops_tasks` | tenant/run、任务类型与幂等键、状态、重试次数、执行租约、策略版本、错误与预算信息；仅处理已采集的新问答，不保存历史回填批次 |

正文可以内联或使用现有存储后端的不可变对象引用；其可访问期必须覆盖复核期。只存内容 hash、当前 Wiki URL、chunk ID 或 Langfuse 深链不满足证据留存要求。重跑验证保留版本，不覆盖原始 AI 判定和人工复核历史。

不复制凭据、密钥等敏感配置。证据访问继承来源权限，并执行运营角色授权；跨租户共享知识和个人记忆不能因进入运营表而扩大可见范围。正文留存、删除、脱敏和访问审计与既有业务规则一致；来源删除或权限变化后，禁止通过旧证据绕过限制。

### 2.3 采集、诊断与分流数据流

```text
启用后新发起的问答 → 最小采集接口 → 独立运行与当时证据记录
                                          ↓
                      持久化任务 → 论断验证与覆盖缺口
                                          ↓
                      根因诊断：链路排查、按需补查与来源比较
                                          ↓
                      风险分流（记录依据、版本和未解决问题）
                         ├─ 满足自动记录条件 → 机器结论留存 → 分层抽检
                         ├─ 高风险/冲突/关键不确定 → 重点人工复核
                         ├─ 采集/工具/任务故障 → 技术排查队列
                         └─ 待补证 → 有界补查 → 重新分流或保留未解决
                                          ↓
                      统一报告、版本化诊断与独立人工复核记录
                      当前流程止于结论留存，不执行知识变更
```

采集与诊断是两个不同职责：在线最小接入保存运行事实和实际证据，后台任务只消费本模块已采集的运行。采集目标是证据进入模型的公共边界及必要来源元数据，不在每个工具里分别实现知识运营逻辑，也不扫描既有消息表补历史数据。

针对 RAG、Agent 和其他入口，先验证公共边界覆盖面；如果现有统一边界不足，只增加捕获事实所必需的薄接入，不能为了减少改动而错误宣称全覆盖。采集方案通过主链路耗时、取消、崩溃及多实例行为验证后再定接口。

有界缓冲或异步落库必须定义丢失语义：不能可靠留存时将运行标记为 partial/unknown，缺少完成记录的运行不能默认为完整。需要可靠投递时复用既有持久任务/存储能力，不自行引入第二套消息系统。

### 2.4 新问答的启用范围与任务恢复

**不做历史问答适配和回填。** 删除旧消息配对、历史模式推断、旧工具结果转换、历史区间盘点、回填批次和回填游标等实施任务，不将这些工作作为一期前置条件。

- 按工作空间记录 `capture_enabled_at`、采集范围和采集策略版本；三类模式使用统一启用口径。存储和比较使用 UTC，展示使用 `Asia/Shanghai`。
- 以请求/运行开始时是否已启用采集决定是否纳入；启用前已开始、启用后才结束的运行不补采。已有会话中的新一轮问答可以纳入。
- 新问答实际使用的多轮上下文、记忆及附件仍属于当次证据；采集这些内容不等于将此前问答逐条导入运营模块。
- 原文和 Wiki 可以早于功能启用时间。诊断仍允许只读查询其内容、来源和修订记录；不做旧问答适配，不意味着不检查知识版本。
- 新运行在起始时记录身份和采集状态；证据部分缺失、取消、空回答、截断和异常分别统计。完全未建立运行记录的采集故障通过入口计数/告警披露，不以运营表行数宣称百分之百覆盖。
- 持久化任务以模块运行记录为基础，支持幂等、重试、执行租约和重启恢复。可扫描本模块未完成任务进行恢复，不扫描旧消息重建问答。
- 再次启用时从新的运行继续采集，不追补停用期间数据。对已采集运行的重新验证、补证及再诊断保留版本。
- 工作台时间筛选仅筛选已纳入运营的运行，明确显示采集启用时间与缺口；不提供“新建回填批次”。机器任务完成、判定通过和人工复核完成分别统计。

按模型并发、预算和错误率配置后台处理速率，支持暂停、恢复和重试。任务恢复不能找回当时未保存的正文，重试也不能把后查材料标记为原始证据。

### 2.5 验证器、诊断器与校准

- 验证模型 workspace 级配置，允许全局默认；尽量避免与生成模型完全相同的自评偏差，但“异族”不是准确性保证。
- 保存生成模型、验证模型实际标识/版本与提示词版本，未知信息不能用当前配置补成历史事实。
- 先用三类模式、不同证据组合、结构化输出、冲突/拒答/缺失等样本校准，再扩大批量验证；20 条只能用于初步试跑，不能宣称代表全业务精度。
- 人工样本既包含 AI 报错，也包含 AI 判为支持的答案，检查误报和漏报。分层抽样的统计保留抽样权重/范围，不直接外推为总体正确率。
- 验证任务幂等键包含 tenant、run/message、答案与证据指纹、验证策略版本；诊断还包含所依赖的验证版本、补查材料版本和诊断策略版本。内容变化生成新版本。
- 分别评估回答判定准确性、根因分类准确性和分流漏报；模型自报置信度不能单独决定免人工。自动记录须结合证据完整性、可检查的比较结果、业务风险及人工样本校准。
- 初期保守分流，完成分模式、渠道及风险层的校准后再逐步扩大自动记录范围；不预设未经验证的置信阈值或抽检比例。高风险案例不因模型高置信而跳过人工。
- 按单条运行与工作空间配置补查次数、模型调用量、并发、时限及费用预算；预算耗尽记为未完成/未解决，不判定为通过。重试、补证及抽检均保留版本与选择依据。

### 2.6 人工复核前的根因诊断

分层执行：全量运行先做确定性的完整性、工具失败与执行路径检查；有足够证据的论断再做回答验证；异常、高风险与抽检案例按需执行较深入的来源、版本及适用条件比较。不能把“未做深查”显示为“知识已核验无误”。

| 关系/问题 | 诊断重点 | 当前产出 |
|---|---|---|
| 回答 ↔ 当时证据 | 错误推断、条件遗漏、引用错配、上下文截断 | 具体问题论断及证据位置，区分生成问题与知识问题 |
| Wiki ↔ 原文 | 归纳错误、遗漏例外、更新滞后、来源不足 | 页面/来源版本、差异片段、适用性及仍待确认点 |
| 原文 ↔ 原文、Wiki ↔ Wiki | 主体、时间、地区、单位和条件一致时是否冲突 | 可比较的冲突对；条件不同则记录差异，不能直接认定冲突 |
| 检索/工具使用 | 是否尝试正确工具、范围是否合理、命中内容是否真正进入上下文 | 检索或执行链路问题；混合模式未调用某类工具本身不算错误 |
| 采集/权限/任务 | 工具失败、正文未保存、权限拒绝、诊断失败 | 技术原因及覆盖缺口，不伪装为知识缺失 |
| 业务知识缺口 | 在明确且有权限的范围内补查后仍缺少所需资料 | 疑似缺口、已查范围与局限；不宣称全库或客观世界不存在答案 |

每份诊断报告至少包含：**回答判定、观察事实、根因候选及排序、支持/反对证据、来源与适用条件比较、已排查原因、未知项、建议分流及需要人裁决的具体问题**。允许多因并存；机器根因结论始终带版本和诊断范围。

补查材料单独存为事后核验材料。拿不到当时来源版本时，可以描述当前差异，但不能断言当时页面已经错误；今天的原文也不能反向证明历史回答当时已被充分支持。来源本身有争议时，诊断输出争议点，不自行指定权威。

诊断通过模块内只读适配器调用检索、页面/原文读取和版本查询；工具采用允许清单，继承来源权限，限制范围与预算。不直接开放具有修改或外发能力的完整 Agent 工具集；无法安全只读调用的能力暂不接入。

### 2.7 风险分流与重复问题归组

| 条件 | 分流方式 | 人工处理目标 |
|---|---|---|
| 低风险、所需证据完整、适用检查完成且满足经校准的通过规则 | 自动记录机器结论，按模式/渠道/来源/风险分层抽检 | 检查漏报和自动记录规则是否有效 |
| 关键准入/额度/期限等高风险结论，或关键规则异常、来源冲突、重要适用性不清 | 优先人工复核，附诊断包 | 裁决具体业务条件、冲突或根因；高风险即使 AI 判为支持也须复核 |
| 证据不足或多个根因无法区分 | 有界补查；仍不足时进入待补证/人工队列并保留未知 | 指明缺哪份资料或哪项判断；不能强制二选一 |
| 采集、工具或后台任务失败 | 技术排查队列，修复采集后按版本重试 | 默认由技术角色处理；涉及高风险业务时同时保留业务复核待办 |
| 低风险异常但尚未满足明确处置规则 | 保留待复核或待补证 | 不因风险较低就将异常自动标为通过 |

自动记录只表示本轮机器处理完成，**不设置人工 confirmed，也不表示知识正确性已获专家确认**。分流必须可解释、可追溯、可重新打开；人工意见触发再诊断时保留旧报告和旧意见。

同一租户和可见范围内，按目标来源及版本、问题类型、适用条件归组重复问题，优先展示代表案例、共用证据和影响规模。每条回答仍保留自身判定与关联；确认某页面有问题不能自动把同组所有回答标为错误。来源版本、适用条件或根因发生变化时拆组/重评，不能仅凭问题文本相似合并。跨权限边界不得借问题组展示受限证据或数量。

一期实现补充（2026-09-29）：存在未知项、待解答复核问题、`unresolved` 根因或来源比较未解决时，不自动合并问题组；无法归组的待办按单条组展示，不隐藏记录。`suspected` 根因在其余归组条件满足时仍可组织为问题组，分组不代表根因已确认。规则适用于新生成的诊断，旧诊断及复核记录保留原版本。

高风险关键词集中维护在 `internal/knowledgeops/constants.go`，沿用一期供应链金融词表和现有匹配方式；此阶段不提供管理端编辑。默认诊断预算调整为 96,000 证据字符、8,192 输出 token、180 秒模型调用超时；后台任务总时限仍为 4 分钟、租约 5 分钟。已有租户保存的预算保持原值，可在设置页调整。

### 2.8 报告和复核工作台

统一入口 `/platform/knowledge-ops`，一期三个 Tab：覆盖与诊断总览、待复核、复核记录。技术待办通过角色与筛选呈现；后续能力在同一模块扩展。

总览展示：

1. 范围内回答数，以及 RAG / Wiki / Wiki + RAG 分布和渠道/实际执行方式/实际来源切面。
2. 可验证、部分可验证、不可验证和处理失败比例；限定证据范围内的论断判定分布。
3. 根因类别、来源核验覆盖、未解决原因、重复问题组数与潜在影响数。
4. 自动记录、待补证、业务复核、技术排查与抽检数量；回答数、问题组数及人工操作次数分别统计，不混用分母。
5. 人工介入比例、复核耗时、积压、机器与人工一致性、抽检发现的漏报，以及单条诊断成本。分层样本保留权重，不把抽检正确率直接当全量准确率。

待复核列表按风险与业务影响排序，展示根因摘要、诊断证据完整性、分流理由、问题组和待裁决事项。专家可按问题组查看共享诊断，但确认范围须明确，不能默认批量覆盖不同回答的结论。

详情页：问题与必要上下文 → 回答论断及当时证据 → 自动根因诊断 → 事后来源比较及支持/反对证据 → 未知项和待裁决问题 → 人工结论。Wiki 证据不强求向量/rerank 分数；历史证据、事后补查和当前页面分别展示。

人工分别确认或纠正**回答判定**与**根因结论**，可以确认其一、对另一项要求补证；记录实际标签、理由和依据，不只有“推翻”布尔值。人工结论可用于再次诊断与校准，不构成修改知识的授权。

复核记录保存追加式人工操作历史和所依据的机器版本。自动记录保留在处理历史中，明确标识机器来源，不冒充人工复核记录。六张 v1.2 图已同步诊断摘要、风险分流、问题归组、双结论复核及自动/人工记录区分。

## 3. 后续二期：全库检查、知识处置与原模式回归

**本章为后续能力，不属于当前只读一期。** 一期已在人工复核前完成按案例触发的根因诊断；二期增加主动知识检查、经审核的变更提案及执行验证，不能以实现诊断为由提前接通知识写入。

### 3.1 从诊断结论到处置建议

一期人工确认回答有错，仅证明该回答问题被确认；知识错误需要独立来源核验。`no_match`、fallback、无引用标签不能直接触发归档或新建 FAQ。后续处置按根因选择原文修订、Wiki 修订、补充资料或问答策略调整，不固定采用修改知识。

一期问题记录可以关联已有 Wiki issues；二期才设计提案与 Wiki 台账的写入、同步及关闭规则。进入二期前单独确认实施范围、审批与执行权限。

### 3.2 主动冲突发现：候选生成与最终判定分开

- 增量：订阅既有文档/Wiki 变更信号或扫描版本变化，等待对应生成/索引状态可用；与周期对账结合。
- 全量：按指定范围分页检查并保存进度，可重试、恢复和限速；不承诺没有盲区，不必引入独立编排平台。
- 候选生成：Wiki 来源关联、`ChunkRefs`、文本规则和可用时的 embedding 近邻。`ChunkRefs` 是已引用分块关联，摘要页可能为空，不能当作完整实体分桶。
- Wiki-only 或无向量索引时使用来源关联与文本候选方法，披露覆盖范围，不要求为了运营强行开启向量化。
- 数字/日期/百分比不同只是候选差异。先比较适用主体、单位、时效与范围，再由规则、模型或专家判定是否冲突；不能让数字规则绕过上下文核验。
- 同时处理原文/Wiki/页面间关系；同源材料不作为独立证据重复计数。

优先验证同一 KB 的关系。多 KB 问答中实际暴露的跨库冲突可以记录并路由，不扩展成一期/二期全局跨库穷举扫描；报告披露该边界。

### 3.3 提案与已有 Wiki 治理衔接

提案带目标类型、版本、问题来源、证据、拟议变更、潜在影响、审核人和原因；区分对原文、chunk、Wiki 页面、FAQ 和问答策略的建议。

- Wiki 问题关联现有 issues、页面修订和修复能力，不创建一套无法互相定位的平行台账。
- 缺口不固定转成 FAQ：先确定应补充的是权威文档、Wiki 组织还是适合 FAQ 的稳定问答。
- 原文和 Wiki 均正确时，不生成修改知识的提案来迎合错误回答。
- 拒绝去重指纹包含目标版本/证据版本和原因；来源变化后允许重新评估，避免 tombstone 永久压制已变化的问题。
- 外部人工纠正导入保留 query、AI/人工结论、依据、时间，并增加来源系统、tenant、request/message 或业务案例标识。原五字段不足以可靠关联时进入待匹配，不能凭相似问题自动定位并修改 chunk。

### 3.4 审批、执行和验证分别记录状态

```text
提案：pending → approved / rejected / expired
执行：queued → running → succeeded / failed / stale
派生更新：pending → ready / failed / not_required
回归：pending → passed / failed / inconclusive
```

专家批准不等于执行完成。执行前检查目标版本、权限与实际差异；版本变化时标记 stale 并重新审核。失败可重试，动作必须幂等，保留执行尝试与错误信息；任务队列状态不能替代业务执行记录。

尽量复用既有写服务，但不再承诺“零新写逻辑”：

| 对象 | 复用方向 | 必须核对 |
|---|---|---|
| chunk/原文 | 既有编辑、修订及重索引服务 | 乐观版本、索引成功状态、来源文件与 chunk 内容一致性 |
| Wiki | 既有编辑/修复服务、修订与问题台账 | 目标版本、来源证据、受影响页面、问题关闭条件 |
| 文档重解析 | `ReparseKnowledge` | 异步完成状态、分块 ID 变化、Wiki 刷新范围，不能仅以请求成功判定完成 |
| FAQ | `UpsertFAQEntries` 等既有能力 | 当前没有可直接复用的 draft 语义；未补全的内容留在提案中，不发布到检索库 |
| 停用/归档 | 目标对象真实存在的启停能力 | 不混淆 Knowledge 与 KB 的字段，不假设文档已有完整 supersession 关系 |
| 冲突披露 | 关联冲突记录与来源范围 | 展示和查询侧接入需明确实施，打标不代表三类问答自动可见 |

不默认调用现有 Wiki 修复 Agent 自由改写即满足“人工审批后执行”；应限制到批准的目标和动作，实际变更超出提案时重新审核。

### 3.5 回归与影响面

- 原模式重跑：RAG 快速流水线、RAG Agent、Wiki、混合 Agent 使用各自实际执行入口；通过模块适配器复用，不复制现有引擎。
- 保留问题、必要历史、附件、知识范围、模型、提示词与工具配置。缺少历史运行配置时标记近似回归，不伪称精确重放。
- 更新前后比较尽量固定非知识变量，并等待索引/Wiki 派生更新完成。Agent 有随机性，关键问题需要重复运行或对照样本；一次翻转不证明稳定修复。
- 同时检查答案支持性、来源适用性、拒答是否合理以及相关问题是否退化，不只统计 unsupported → supported。
- 工具回归不产生非预期外部副作用：涉及写操作、消息发送、MCP 等时使用明确的只读/受控适配；无法复现的能力标记不等价，不能静默删除工具后声称同模式通过。
- 影响面关联实际使用的 chunk、文档、Wiki 页面及来源关系，区分直接使用与派生影响；历史关联不完整时给出已知下界/未知部分。
- “潜在受影响回答数”不是“已确认错误回答数”。按当前 `knowledge_references` 反查 chunk 的 count 只能作为部分线索。

## 4. 工程聚合与 main 合并兼容性

### 4.1 目标与取舍

**聚合的是业务职责和变更位置，不是把所有代码塞进一个大文件。** 核心问答流程只产生事实或调用窄接口，不承载判定、任务恢复、报表和提案策略。避免为本模块重构整个问答引擎或复制上游代码。

不能保证后续合并绝不冲突；目标是让冲突集中在少量、可解释、可测试的接线位置，并通过契约检查发现“文本合并成功但语义不兼容”的情况。

### 4.2 建议文件边界

以下为后续实现的目标布局，当前尚未创建这些文件；按阶段增加，不提前搭建空框架。

```text
internal/knowledgeops/
  model.go / ports.go / config.go    模块模型、窄接口、配置与 schema 版本
  capture.go / normalize.go          采集接收、来源归一化、完整性判定
  recovery.go                       已采集运行的任务恢复与状态对账
  verify.go / diagnose.go            回答验证、只读根因诊断
  triage.go / grouping.go            风险分流、抽检与问题归组
  review.go / report.go              独立结论复核、统计
  repository.go / tasks.go           独立表持久化、幂等任务及注册适配
  http.go                           模块 API 与权限调用
  adapters/                         一期消息、工具、Wiki 只读适配；后续扩展写服务/回归
  prompts/                          模块自己的验证/诊断提示词
  *_test.go                         对应职责的单元和契约测试
  proposal.go                       二期按需增加的知识变更提案
  execute.go / replay.go             二期执行与回归

internal/container/knowledge_ops.go       集中依赖装配、启停与生命周期
internal/router/routes_knowledge_ops.go   集中 HTTP 注册
internal/router/task_knowledge_ops.go     集中任务注册，覆盖标准/Lite 接入

frontend/src/views/knowledge-ops/         页面与模块组件
frontend/src/api/knowledge-ops.ts         模块 API
frontend/src/router/knowledge-ops.ts      导出的模块路由
frontend/src/views/knowledge-ops/locales/ 模块文案，按语言导出

migrations/versioned/                     PostgreSQL 增量迁移
migrations/sqlite/                        SQLite 对应增量迁移
```

具体文件拆分以单一职责为准。模块内部避免循环依赖：核心服务依赖模块 ports；adapters 依赖核心及既有服务；装配层把二者连接，核心不反向导入 adapters。既有共享 types/interfaces 只在必要接入契约中使用，不把知识运营领域对象散布到全局。

前端现有语言文件位于 `frontend/src/i18n/locales/`，由 `frontend/src/i18n/index.ts` 加载。模块文案集中在自身目录，在现有语言文件中导入命名空间，并保持语言审计/生成机制兼容，不为此重构全局 i18n。

### 4.3 允许修改现有文件的接入清单

| 接入位置 | 允许的最小修改 | 必须留在模块内的逻辑 |
|---|---|---|
| `internal/container/container.go` | 调用集中注册函数，连接已有生命周期 | 构造、配置、调度、清理 |
| `internal/router/router.go` | 添加必要依赖与单个路由注册调用 | 端点定义、参数解析与业务处理 |
| `internal/router/task.go` 及现有 Lite 注册位置 | 调用模块任务注册，复用任务执行抽象 | handler、幂等、执行租约与重试语义 |
| 公共运行/证据边界 | 传递身份、实际可读内容和结束事实给可选采集接口 | 证据分类、持久化、判定和报表 |
| `frontend/src/router/index.ts`、实际菜单/i18n 索引 | 导入模块路由、导航与文案 | 页面状态、组件和业务交互 |
| 权限/系统设置的集中注册处 | 注册模块能力和设置键 | 默认值解释、模块策略；后端权限仍须真实执行 |

公共采集边界在一期接入验证中根据真实调用链确定并形成清单，不能先假定一个事件已覆盖所有入口。优先构造注入的 Observer/Sink 或已有事件订阅，无需采集时使用 no-op；避免新增全局可变单例和工具内散落的条件分支。

如果必须传递新来源版本等元数据，采用可选、向后兼容字段和单处生产/消费约定；未知版本明确标记，不根据当前页面猜测。若最小字段仍无法支持准确性，则调整采集设计，不能仅追求修改行数少。

### 4.4 明确禁止的扩散方式

- 不在 `qa.go`、`engine.go`、每个 Wiki/RAG 工具、每个渠道 handler 中分别塞入验证模型、提案或数据库逻辑。
- 不复制 `AgentQA`、RAG 流水线、Wiki 生成器或现有写服务，防止长期维护两份引擎。
- 不为采集证据取消现有 `agent_steps` 裁剪或改变历史重放、SSE、引用标签的既有行为。
- 不大规模调整上游目录、通用接口签名、格式或 import 顺序来“顺便整理代码”。
- 不用全量模型 prompt/用户数据永久日志代替最小必要证据采集；不把业务证据依赖强绑到 Langfuse。
- 不为减少 merge 冲突绕过权限、版本检查、完成状态或数据完整性。

### 4.5 配置、数据迁移与提交边界

- 模块使用独立配置结构和 `knowledge_ops.*` 设置命名，默认禁用；优先沿用既有配置/设置服务，只增加必要注册，不重排全局配置文件。
- 新表、任务与 API 使用独立命名空间；保持已有业务表和外部响应兼容。任务 payload、证据和验证策略分别有版本，适配旧任务与历史记录。
- 优先新增独立表，只有确实无法在旁路关联表达时才提出核心表变更；在设计和 PR 中说明原因。
- PostgreSQL 与 SQLite 使用项目现有迁移机制，禁止模块启动时自行 AutoMigrate；明确项目支持矩阵，不顺带承诺其他未验证数据库。
- 迁移编号在实现时根据最新目标 main 分配，集成前检查冲突。尚未发布的分支迁移可以按仓库规范协调编号；已在环境应用的迁移不得重写、改号，应新增兼容迁移。
- 按“模块独立实现 / 核心接线 / 迁移 / 前端接入”组织可审查提交，避免混入无关重构。不要把必要配套拆成可被错误单独上线的状态。
- Swagger 等生成产物在接入完成后统一生成并检查，不把无关生成差异混入功能变更。

### 4.6 main 合并后的语义检查

每次集成上游变更，除解决文本冲突，还检查以下契约：

| 上游可能变化 | 必须验证 |
|---|---|
| 消息完成/更新语义 | 取消、续写、空回答、迟到更新仍能正确归类和幂等处理 |
| 工具返回格式、裁剪位置 | 新适配器仍能识别实际正文、版本和截断，不把未知格式当完整 |
| 模型上下文与引用处理 | 记录的是实际可读内容，引用映射仍可追溯，候选未读内容不混入 |
| Wiki 来源/修订结构 | 当前版本与历史证据不混用，未知字段显式降级 |
| 权限与共享范围 | 跨租户、个人上下文与已撤销权限不因运营访问而泄漏 |
| 任务、配置、迁移和路由注册 | 开关、标准/Lite 两种执行、重试和数据库升级兼容 |
| 写服务及问答入口（后续二期） | 执行版本检查、派生更新完成和原模式回归保持语义；一期校验诊断不调用写入能力 |

将上述变化集中在 adapters 和少量装配文件处理。维护三类模式的脱敏固定样本与边界契约测试；合并成功但契约失败时，不以“能编译”作为兼容结论。

## 5. 实施顺序与验收门槛

v1.0 的“一期约 10 天、二期约 4 周、已定稿可开工”不再作为承诺。先完成当前入口与最小采集接入验证，再按接入面、证据留存和诊断能力重新估算；历史数据工作已从范围移除。下表是任务边界；本轮已获授权实施 B、C、D 的一期能力，A 不包含历史数据工作。

| 阶段 | 可交付结果 | 验收要求 |
|---|---|---|
| A：当前入口与采集契约确认 | 三类模式、渠道、运行边界、实际证据与元数据清单 | 不盘点旧问答；明确 RAG 执行方式、启用口径及新问答采集缺口 |
| B：模块边界与采集接入 | 运行/证据记录、开关、集中适配与接线清单 | 不改既有问答语义；采集失败不影响回答但能被发现；正文和版本来源可追溯 |
| C：一期验证与诊断 | 新问答任务恢复、回答验证、来源比较、只读根因报告 | 幂等可恢复；事实与假设分开；三类模式、结构化输出及未知版本有校准样本 |
| D：一期分流与重点复核 | 风险分流、问题归组、抽检、双结论复核、报告 | 诊断先于人工；自动记录不冒充人工确认；不修改知识；高风险及未解决案例不静默通过 |
| E1：二期全库检查与提案 | 主动知识检查、可审核变更与影响面 | 不从回答错误直接推导知识错误；复用 Wiki 台账；权限与版本明确 |
| E2：二期执行与原模式回归 | 执行、派生更新、回归独立状态 | 不能只用固定 RAG 宣称 Wiki/混合回归通过；回归副作用受控 |
| F：在线防线 | 经业务校准的门控与拒答 | 有分模式误报、漏报、覆盖率和延迟指标，经过单独上线评审 |

A 的入口核对与 B 的最小采集设计可以并行推进；历史数据适配不作为前置工作。扩大新问答采集与自动分流范围前，完成对应覆盖与校准验证。先交付 B 的可验证采集切片，再完成 C、D，不能把诊断无限后移到人工复核之后。后续各阶段实施计划列出创建/修改文件、输入输出契约、测试与回退方式；具体交付与限制以开发验收说明为准。

必要验证场景：
- [ ] 三类模式均有成功、无命中、证据部分缺失的脱敏样本；RAG 快速/Agent 执行单独覆盖。
- [ ] 混合配置只使用 Wiki / 只使用原文 / 两者都用，统计与判定均正确。
- [ ] Wiki 支持回答但与来源不一致，两个结论不混淆。
- [ ] `read_document` 裁剪、Wiki 截断、未知工具结果不被误认为完整证据。
- [ ] 关闭引用、JSON 输出、合理澄清/拒答，不因无标签误判为幻觉。
- [ ] 启用前开始的运行及停用期间问答不补采；旧会话中的新问答可正常纳入，多轮上下文按当次使用留存。
- [ ] 已纳入运行的取消、迟到完成、重复投递、重启和多实例任务恢复无静默漏项或重复有效记录；采集失败可见。
- [ ] 来源更新/删除、权限撤销和跨租户共享仍受正确访问控制。
- [ ] 验证模型故障、采集故障、预算耗尽有可恢复状态，问答主流程不依赖验证成功。
- [ ] 复核前已有诊断报告；因缺证、预算或失败不能完成诊断的案例明确显示原因及待裁决项。
- [ ] 自动记录与人工确认分开；高风险、来源冲突和未解决异常不因模型高置信或预算耗尽而通过。
- [ ] 回答判定与根因结论可分别确认/纠正，补查不反写为原始证据；重跑保留旧版本和人工操作。
- [ ] 重复问题归组不越权、不把潜在影响当已确认错误，不自动覆盖成员回答结论。
- [ ] 诊断允许清单和调用记录可证明不调用知识修改、Wiki 问题写入、重解析、归档或消息外发能力；人工确认也不触发写入。
- [ ] 技术失败进入技术待办，高风险业务复核同时保留；抽检能覆盖 AI 判为支持的样本。
- [ ] 后续二期：提案批准后目标版本变化、索引失败、Wiki 尚未更新时不能显示完成。
- [ ] 模块禁用和启用分别验证，PostgreSQL/SQLite、标准/Lite 支持范围明确。
- [ ] 合并 main 后运行模块单元测试、适配契约测试和必要的原问答回归；仅文档更新不运行应用测试。

## 6. 远期在线防线

只有验证器与诊断结论经过业务校准后，才考虑线上门控：

- 检索/工具阶段：检查来源可用性、适用范围和已知冲突；Wiki 没有向量分数时不能硬套 RAG rerank 阈值。
- 生成完成、对外发布之前：检查关键论断是否得到证据支持。必须先有候选答案，不能将事后论断验证简单移到生成前。
- 流式回答涉及暂存、延迟或分段发布策略，需另行设计；已经发送的内容不能事后视为被拦截。
- 关键准入/额度/期限与概括性问答采用不同策略，记录拒答原因、误拒、漏放和覆盖率。
- 三类模式分别确定接入位置；不能只在 `chat_pipeline` 的 rerank 后增加一个检查就宣称覆盖 Agent/Wiki。

## 7. v1.2 变更摘要

- 将较完整的按案例根因诊断提前到一期、人工复核之前，明确观察事实、根因候选、支持/反对证据及待裁决问题。
- 增加风险分流、自动记录、技术排查、分层抽检和重复问题归组，减少专家逐条调查；高风险和未解决异常不自动通过。
- 明确一期只写运营记录，不修改知识；Wiki 问题登记、修复、提案执行及原模式回归留到后续阶段。
- 分离回答判定、诊断结论、分流与人工复核记录；追加保存版本，禁止把自动记录标为人工确认。
- 补充诊断预算、只读工具边界、校准和分流漏报指标，调整模块布局、实施阶段及验收门槛。
- 按最新范围移除历史问答适配、扫描、留存区间盘点及回填，改为启用后新问答采集；保留既有会话上下文、知识修订只读诊断和模块任务恢复。
- 延续三类模式、证据真实性、集中模块及 main 合并兼容约束；不以本地测试数据推导真实覆盖。
- 六张设计图重绘为 v1.2，替换旧图并同步浏览页与方案引用；保留可编辑 SVG、PNG 和绘图源文件。一期开发继续遵守不执行历史回填、不修改知识的边界。
