## 交付范围

独立后端模块 `internal/knowledgeops`，配套 Vue 工作台 `/platform/knowledge-ops`。过程为：新问答采集 → 证据支持性验证 → 只读来源及根因诊断 → 风险分流 → 双结论人工复核/抽检 → 追加记录。

- 兼容快速 RAG、Agent RAG、Wiki、Wiki + RAG，记录实际入口与执行方式。身份或模式不能确定时保留 unknown。
- 候选来源仅保存标识，实际发送给模型的来源保存转换后的片段；事后补查另行标识，不能用来证明原回答已得到支持。
- 诊断保存论断、证据引用、事实、根因候选、反对依据、未知项、待裁决问题、范围、模型及策略版本、token 和耗时。
- 高风险、冲突、未解决事项不能自动记录为通过。自动记录默认关闭，需要管理员登记校准依据后显式开启；自动记录始终是机器结论。
- 回答与根因分开复核，根因具有人工分类标签；记录绑定机器分析版本、实际标签、动作、理由和操作者。重新诊断生成新版本，旧记录保留。
- 模块仅写入 `knowledge_ops_*` 六张表，不调用 Wiki、原文、FAQ 写入/重解析/修复接口。

## 启动与验收步骤

1. 切换到上述独立工作区，沿用项目原有开发启动方式。不要把原目录的未提交内容覆盖到此工作区。
2. PostgreSQL 使用项目标准迁移流程 `make migrate-up`，新增版本为 `000110_knowledge_ops`。Lite/SQLite 使用原有启动迁移，新增版本为 `000027_knowledge_ops`。本次开发测试使用临时 SQLite 和隔离 PostgreSQL，没有迁移用户现有数据库。
3. 管理员或 Owner 登录，进入“知识运营”，选择可用的 KnowledgeQA 模型后启用采集。默认仅人工分流；先保留自动记录关闭。
4. 启用后各发起一次 RAG、Wiki、混合问答；总览应出现渠道、模式、采集完整性和实际回答。启用前消息不会导入。
5. 等待后台诊断，检查模型可见证据、事后补查、根因、未知项和分流原因。来源版本不明或缺失不能显示为已核验无误。
6. 在待复核页分别提交回答与根因结论，检查记录页的两个对象和实际标签。重新诊断后旧版本仍在，旧页提交须提示版本已变更。
7. 关闭采集，发起新问答应不再新增记录；待处理任务暂停，已经领取的任务可能完成；既有记录保留。

后台单实例顺序处理，3 秒轮询；任务租约 5 分钟，异常退出后租约到期可再次领取。新运行若超过 1 小时没有采集心跳，恢复为采集中断，不伪造回答或补历史消息。诊断超时默认 90 秒；补查最多 15 秒。来源数量、字符数和采集数据库耗时均有预算，超出会标为缺口。

## 权限与证据边界

运营控制台仅管理员/Owner 的人类登录可用，API key 不开放这些管理接口。仍遵循既有会话规则：个人 Web 会话只有本人可见；管理员可以查看租户渠道会话，并不获得其他人的私人 Web 会话。列表、总数、详情、复核记录均使用相同权限检查。

每次读取重新检查来源 KB 权限及文档/chunk/Wiki 是否仍可用。任何已关联来源被撤销或删除，整条记录不返回。后台处理 Web 问答时重新检查当前成员和用户状态；无法重建机器调用跨租户权限时保守拒绝补查，不扩大权限。

不保存完整系统提示、隐藏推理和图片 data URI。对已识别的凭据模式进行脱敏，并标明缺口。问题、答案及有来源绑定的实际片段用于诊断；历史/记忆等不能独立验证权限的文本不复制为无来源的证据。

## 当前实现的明确限制

- 自动化用例使用模拟诊断模型，证明状态、权限、证据约束及任务闭环；不是业务准确率校准。正式启用自动记录前仍须以真实三类模式、渠道及风险分层样本人工校准，并登记依据。
- RAG 检索结果若没有可信的来源修订号，保留 unknown。不会用当前数据库版本冒充当时版本；该类记录保守补证。
- Wiki 来源比较仅针对当次已读页面关联的当前文档/chunk。页面版本漂移、文档级关联、超出预算或缺少关联时保留未解决，不能宣称检查了全库或重建了历史版本。
- 不支持的工具、记忆、附件、历史压缩、未绑定来源，以及 Wiki 邻接页摘要会显示相应缺口。不会把缺口样本纳入自动通过。
- 已支持按问题组查看及展开组内案例；仅同来源、版本和适用范围的已授权待办归组，相关来源版本缺失时独立处理。不支持一键批量确认整个问题组。
- 抽检记录概率、模式/渠道/风险/来源核验层。页面显示的是证据支持性分布，不是业务正确率；token 是消耗量，不冒充货币成本。
- 第一版查询在有界批次内逐条重新验证权限，超时返回明确错误，不返回部分统计。待办优先排序、问题组及复核历史在授权过滤后聚合，内存占用随匹配记录数增长，未做生产规模压测。数据量扩大后可在保持同等撤权语义的前提下优化查询。

## 合并 main 的接入面

大部分实现是新增独立文件。现有文件只保留采集接口调用、Wiki 来源元数据、容器/路由注册及菜单/页面入口。重点检查：

- `session*.go`：启用边界和结束回调仍对应实际运行；流式异常和取消不变成成功。
- `agent/{act,think}.go`、`chat_pipeline/chat_completion*.go`：采集必须位于实际模型输入编码之后；工具候选不能冒充实际输入。
- `agent/tools/wiki_tools.go`、`types/agent.go`：来源修订号来自本次读取；内部元数据不改变原对外返回格式。
- 容器和路由：只有一个模块注册点，不引入 SessionService 的依赖循环；默认关闭不影响问答。
- 前端菜单/路由：保留原权限语义和现有国际化约定。
- 新迁移号若在尚未部署时与 main 新迁移重号，统一重编号并重跑迁移测试；不要重写已应用的迁移。

回退功能先关闭采集/诊断设置，再部署旧代码。默认保留运营表作为记录；执行 down 会删除本模块全部数据，应作为单独的明确清理操作，不是日常关闭功能。

## 核心逻辑对齐修订（2026-09-28）

页面无需逐像素复制设计稿，但以下业务契约必须成立。本次改动集中在知识运营模块内部，没有增加现有问答流程接线或数据库迁移。

| 环节 | 当前实现与验证 |
|---|---|
| 观测 | 总览分别展示模式 × 证据完整性交叉统计、回答支持性、来源一致性、根因候选和分层抽检；机器判定与来源核验不合并为“正确率” |
| 诊断先行 | 待复核直接展示根因摘要、未解决项和待裁决点；详情首屏展示诊断，运行及模型元数据折叠，证据与复核并排 |
| 风险分流 | 全部已授权待办先按风险、再按同风险下最早诊断排序，随后分页；不虚构业务影响分数。各队列可重叠，技术故障不随业务复核消失 |
| 减少重复调查 | `/groups` 按已有保守指纹聚合，可展开组内案例；未知来源版本不归组。数量仅表示筛选范围内的可见待办，不能等同已确认错误 |
| 重点复核 | 回答/根因分别保存；人工要求补证的自动记录也进入补证队列。没有整组批量确认，组内其他回答的结论不受影响 |
| 追溯 | 记录页对照问题、绑定版本、机器原结论与人工结论；按复核时间、对象、动作、人员和理由筛选；进入详情定位历史版本且只读 |
| 抽检 | 展示最新诊断中纳入抽检、两项复核完成、发生人工纠正的回答数；不把纠正计数当作已校准漏报率 |

新增后端回归覆盖全局优先排序、权限过滤后的归组数量、覆盖与来源分开统计、历史机器结论绑定、人工补证待办及未知版本不归组；前端增加复核时间转换用例。页面 smoke 新增问题组展开、待裁决点可见、诊断首屏和历史版本只读检查。截图使用模拟 API，仍不代表真实模型端到端校准完成。

### 筛选区域界面修订

总览、待复核和复核记录统一使用独立 `FilterBar.vue`：搜索及时间范围置顶，常用条件紧凑排列，证据完整性、回答判定、风险及根因分类收进“更多筛选”。日期使用 TDesign 范围选择器，可选择最近 7/30 天，继续按包含起点、不含终点转换为 UTC 请求参数。生效条件显示可移除标签；草稿条件只有应用后才查询。页面截图和 smoke 已验证日期、风险、搜索参数及标签移除，未修改后端业务逻辑。
